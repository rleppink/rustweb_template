# AGENTS.md

Rust 2024 (toolchain pinned `1.97.1` in `rust-toolchain.toml`), axum 0.8 + SeaORM/Postgres, vertical-slice architecture. Workspace members: `.` (app) and `migration`. See `README.md` for the full design rationale.

## Verify before finishing

CI enforces `-D warnings`; the workspace lint set makes `unwrap_used`/`expect_used`/`indexing_slicing`/clippy-pedantic warnings and `todo!`/`unimplemented!`/`unsafe_code` errors. Write warning-free code and check with the same commands CI runs:

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features
cargo run -p tidy          # architecture checks: slice boundaries, DTO casing, OpenAPI drift
cargo test --workspace --all-features
```

`tools/tidy` is a stable-toolchain architecture checker (workspace member,
CI step "Tidy", `just tidy` / `just tidy-update`). It enforces the slice
rules below that clippy cannot see: SeaORM/entity imports confined to
`service.rs` (+ a tiny allowlist), `HttpError` confined to handlers,
`features/<feature>/<verb>/` having `mod.rs` (`handler.rs`/`service.rs` are
optional conventions — handler code is identified by its `#[utoipa::path]`
attribute, and the import rule forces `service.rs` the moment a handler
needs sea_orm, no matter which file the handler lives in), every
`tag = "stores"` route declaring `security`, no user ids in paths, camelCase
`ToSchema` DTOs, entities never deriving `Serialize`, `std::env` only in
`config.rs`, and `src/features/declared_paths.rs` (the const the router test
iterates) regenerated from the `#[utoipa::path]` attrs. Adding a route:
`just tidy-update`, then commit the regenerated file. Tidy needs no
database; run it from the workspace root.

Tests need `DATABASE_URL` pointing at a postgres where the user can create databases (`docker compose up -d postgres` — the compose superuser qualifies); each test gets a fresh scratch database that's dropped on teardown. Run the whole suite, not a single test, when changing shared code (router, auth, test_support).

## Layout and rules

- One folder per slice under `src/features/<feature>/<verb>/` with `mod.rs` (exports `route()`) at minimum. `handler.rs` is the conventional home for the HTTP surface and `service.rs` the conventional home for domain logic — both optional: a thin slice may place its handler next to `route()` (tidy recognizes handler code by its `#[utoipa::path]` attribute, not by filename), and only the moment handler code needs SeaORM does the import rule force a `service.rs`. `features/<feature>/mod.rs` exposes `routes()` merging each verb's `route()`; `src/router.rs` merges features into the app.
- `users.password_hash` must never be serialized; always return DTOs, never entities.
- Validation is duplicated per slice **deliberately** (rule of three in README). Do not extract shared validation until a third slice needs it.
- New routes must carry `#[utoipa::path]` with the correct `path` and be merged into the router. `src/router.rs` has a test asserting the `declared_paths.rs` set (generated by `tools/tidy` from the attrs) is exactly what `/openapi.json` serves — after adding a route run `just tidy-update` and commit the regenerated file.
- `src/config.rs` is the only place env vars are read (typed `Config`, fail-fast). New settings: add a field + env parse + `.env.example` + README table. Never read `std::env` in slices.
- Email goes through the `Mailer` trait (`src/mail.rs`), injected via `AppState`. `LogMailer` is the dev implementation (logs reset links — never use in prod); tests inject `TestMailer` from `test_support` and inspect `sent()`.

## Test helpers

`src/features/test_support.rs` has everything slice tests need; don't reinvent them:
- `test_db()` — handler tests; creates a uniquely-named scratch postgres database, returns `(DatabaseConnection, PostgresStore, TestDbGuard)`. Keep the `_guard` binding — it drops the database (with `FORCE`) when the test ends, and the test FAILS if the drop fails (a warning only when the test is already panicking). A failed setup also drops the DB, never orphaning it.
- `test_connection()` — service tests (no session store); returns `(DatabaseConnection, TestDbGuard)`, keep the `_guard` binding too.
- `insert_user`/`insert_post` bypass the business layer (independent slices); `register_user_direct`/`register_and_login` produce real argon2 hashes.
- `request(app, method, uri, body, cookie)` drives the router via `tower::oneshot`; it injects a `ConnectInfo` extension for `127.0.0.1` (the rate limiter's key). `request_from(..., peer)` speaks as another IP — the router's rate-limit tests use it.
- `test_config()` — a Config with generous rate limits and TLS off; build apps with `app_router` (defaults), `app_router_with(db, store, config, mailer)`, or `app_router_with_mailer`.
- `TestMailer` records `SentMail { to, token }`; password-reset tests read `mailer.sent()` to get raw tokens.

## Gotchas

- Config comes from `Config::from_env()` in `src/config.rs`: `DATABASE_URL` required, `PORT`/`COOKIE_SECURE`/`AUTH_RATE_LIMIT_*`/`PASSWORD_RESET_TOKEN_TTL_MINUTES`/`PUBLIC_BASE_URL` optional. `cargo run` needs a running postgres — `docker compose up -d postgres` and `DATABASE_URL=postgres://rustweb:rustweb@localhost:5432/rustweb` (or copy `.env.example`). Migrations + session-store migrations run at startup.
- Session cookie: `id`, `Secure` only when `COOKIE_SECURE=1` (defaults off for plain-HTTP dev), SameSite=Strict, 14-day inactivity expiry, rotated on login. New protected handlers take the `CurrentUser` extractor (`src/auth.rs`).
- All `/auth/*` routes (including new ones) sit behind the per-IP governor layer in `src/router.rs` — no per-slice work needed. `main.rs` must keep `into_make_service_with_connect_info::<SocketAddr>()` or the limiter has no peer to key on and rejects everything.
- DB timestamps are chrono (`sea_orm::prelude::DateTimeWithTimeZone` = `chrono::DateTime<FixedOffset>`); `time` is only the session-expiry crate. `chrono::Utc::now()` converts with `.into()`.
- Docker dev loop (`just dev`): compose runs a `postgres:18` service and hardcodes the dev container's `DATABASE_URL` to it (host `.env` is ignored). Postgres 18 keeps data in `/var/lib/postgresql` — the `pg_data` volume mounts that directory, not the old `data` subpath. Editing `Cargo.toml`/`Cargo.lock` invalidates the image's dep cache — the next `just dev` takes minutes; `just remove` wipes volumes (DB + build cache) to re-seed from the image.
- No existing convention beyond the single "Initial skeleton project" commit; follow conventional-style subject lines if committing.
